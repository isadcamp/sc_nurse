# Sprint 13 — ปิดงานค้าง UI Tailwind และความถูกต้องของการจัดเวร

สถานะ: วางแผนแล้ว งานค้างด้านล่างยังไม่ถือว่าเสร็จ
วันที่จัดทำ: 2026-09-15
ต่อเนื่องจาก: [Sprint 12](plan_s12.md)
มาตรฐาน: [Development Rules](rule.md)
ที่มา: การตรวจโค้ดล่าสุดและผลทดสอบหน้าจัดเวรในบทสนทนา ไม่ใช้สถานะจากแผนเก่าแทนหลักฐานปัจจุบัน

## 1. เป้าหมายและขอบเขต

ให้หัวหน้าหอผู้ป่วยใช้ UI ใหม่ได้ครบตั้งแต่เตรียมข้อมูล จัดเวร ตรวจปัญหา ส่งตรวจ อนุมัติ ประกาศ และพิมพ์ โดยตัวเลขบนหน้าจอตรงกับนโยบายและผลคำนวณของระบบ

- คง Next.js, Go, MySQL และ Tailwind CSS ที่ติดตั้งแล้ว ไม่สร้างระบบใหม่ซ้ำ
- ยึดภาพ NurseFlow โทนฟ้า–ขาวที่ผู้ใช้เลือก: ตารางกว้าง เมนูย่อได้ เครื่องมือเหนือตาราง และแผงปัญหาพับได้
- รองรับคอมพิวเตอร์และแท็บเล็ต ใช้ API และข้อมูลจริงในเส้นทางใช้งานปกติ
- ลำดับงาน: ความถูกต้องของข้อมูลและการบันทึก → ตั้งค่าครบ → workflow → ตรวจ UI และพิมพ์ → นำร่อง
- ไม่เพิ่ม AI engine ใหม่, SSO หรือเชื่อม HIS ใน Sprint นี้ และไม่ deploy/migrate ฐานใช้งานจริงโดยอัตโนมัติ
- กฎ clinical policy, อัตรากำลัง และเป้าชั่วโมงต้องมาจากหน่วยงาน ห้ามสมมติค่าเพื่อทำให้ผลตรวจผ่าน

## 2. จุดเริ่มต้นที่ยืนยันแล้ว

| ส่วน | สถานะและข้อจำกัดหลักฐาน |
|---|---|
| Tailwind CSS | ติดตั้ง Tailwind/PostCSS จริงแล้ว พร้อมฟอนต์ Noto Sans Thai และ Heroicons |
| Layout หน้าจัดเวร | มีเมนูย่อได้ แถบเลือกเวร แผงปัญหา และตารางตรึงหัว/ชื่อ |
| การเลือกเวร | ใช้รหัสจาก roster และรองรับช่องที่ยังไม่มี assignment; เคยทดสอบบันทึกเวรเช้าสำเร็จด้วย fixture |
| หน้าต่าง | มี ModalFrame/SidePanel และการรองรับคีย์บอร์ดในโค้ด ยังต้องทดสอบการทำงานครบ |

| การตรวจโค้ด | lint และ TypeScript ผ่านในการตรวจล่าสุด; build เคยผ่านก่อนการแก้รอบหลัง ต้องรันใหม่กับชุดส่งมอบ |
| ภาพหน้าจอ | มี desktop-initial.png และ desktop-edited.png ที่ tests/e2e/test-results/ui-review/ ขนาด 1586×992; ไม่พบ page error ในเส้นทาง login/open/edit ที่ตรวจ |
| การตรวจรับ | ยังไม่มี design-qa.md และยังไม่มีหลักฐาน E2E ครบ workflow ของ UI ใหม่ |

ข้อควรระวัง: รอบก่อนคำสั่งแก้ CoverageSummaryRow และ backend สำหรับล้างเวรถูกปฏิเสธก่อนเริ่มทำงาน ตรวจไฟล์แล้วการแก้เหล่านั้นยังไม่อยู่ในโครงการ ห้ามนับว่าเสร็จ

## 3. แผนดำเนินงาน

### S13-01 — ล้างเวรให้ทำงานครบถึงฐานข้อมูล (P1)

หลักฐาน: ปุ่มล้างเวรส่ง shiftCode ว่าง แต่ backend/internal/service/roster.go ยังยอมรับเฉพาะรหัสใน roster.shifts และ validator ยังมองรหัสว่างเป็นข้อมูลไม่ถูกต้อง

- [ ] กำหนด contract ของ PUT /api/v1/schedules/{id}/assignments ให้ shiftCode ว่างหมายถึงยังไม่ได้จัดเวร โดยแยกจาก X/OFF และ L อย่างชัดเจน
- [ ] เก็บเซลล์ที่ล้างเป็น assignment ว่างพร้อมเพิ่ม version เพื่อป้องกันคำขอเก่าทับข้อมูลหลังล้างและลงใหม่ ไม่ลบประวัติหรือรีเซ็ต version
- [ ] ปรับ service, validator และ persistence ให้รองรับค่าว่าง โดยคงสิทธิ์ head, สถานะที่แก้ไขได้, การตรวจ version, เวรล็อก และการตรวจซ้ำของรายการต่อวัน
- [ ] ค่าว่างต้องไม่เพิ่มชั่วโมง วัน OFF วันลา โควตาเวร หรือกำลังคน แต่ยังต้องตรวจผลกระทบต่อกฎของทั้งตารางก่อนบันทึก
- [ ] ไม่บังคับ override อัตโนมัติ หากการล้างทำให้ผิดข้อบังคับ ให้แสดงปัญหาและใช้กระบวนการยกเว้นที่ระบบอนุญาตเท่านั้น
- [ ] ปุ่มแสดงกำลังบันทึก ป้องกันส่งซ้ำ และรักษาค่าเดิมเมื่อ API ปฏิเสธ

เกณฑ์ผ่าน: ลงเวร → ล้าง → โหลดใหม่ยังว่าง → ลงใหม่ได้; viewer/เวรล็อก/ฉบับประกาศถูกปฏิเสธ; stale version ไม่ทับข้อมูล; มี audit และ MySQL integration test ยืนยันการคงอยู่ของข้อมูลหลัง restart

### S13-02 — ใช้กำลังคนและชั่วโมงจากข้อมูลจริง (P1)

หลักฐาน: CoverageSummaryRow ใช้เป้า 3/2/2, NurseStatsColumn ใช้เป้า 160 และชั่วโมงคงที่ตามรหัส, ShiftBadge มีข้อความเวลาเวรคงที่

- [ ] ใช้ summary service เป็นแหล่งข้อมูลร่วมสำหรับหน้าจัดเวร ภาพรวม และ export; ตรวจการคำนวณ summary ก่อนเชื่อม UI โดยเฉพาะเวรข้ามวัน/รอยต่อเดือนและ RN/PN
- [ ] แสดงกำลังคนตามช่วงเวลาที่นโยบายกำหนด พร้อมจำนวนจัดได้/ต้องการ และแยกปัญหาคุณสมบัติ RN/PN/หัวหน้าเวร แม้ยอดรวมคนครบ
- [ ] ใช้เป้ารายบุคคล ชั่วโมงจากช่วงเวรจริง และข้อมูล carry-in/carry-out ตามความหมายของ summary แทนค่าคงที่ใน frontend
- [ ] ชื่อ เวลา และคำอธิบายเวรมาจาก roster.shifts; แผนที่สีเป็นเพียงการนำเสนอ ไม่เป็นแหล่งกฎธุรกิจ
- [ ] ถ้าไม่มีนโยบายหรือโหลด summary ไม่สำเร็จ ให้แสดงสถานะชัดเจน ไม่เติมเป้า 3/2/2 หรือ 160 แทน
- [ ] รีเฟรช summary หลังแก้เวร/ใช้ผล AUTO/เปลี่ยนนโยบาย และไม่แสดงผลเก่าปนกับหน่วยงาน เดือน หรือฉบับใหม่

เกณฑ์ผ่าน: ตัวเลขในตาราง ภาพรวม และ Excel ตรงกันสำหรับ fixture เดียวกัน รวมเวรควบ เวร 12 ชั่วโมง เวรข้ามวัน วันลา วันหยุด และเป้ารายบุคคลต่างกัน

### S13-03 — ตั้งค่านโยบายและประเภทเวรให้ครบ (P1)

หลักฐาน: PolicyModal ส่ง targets/preferences/staffing เดิมกลับไปโดยไม่มีฟอร์มแก้ครบ; GET /api/v1/shift-types ยังคืนรายการว่าง; ShiftTypeRepository ยังบันทึก periods เป็น []

- [ ] เติมฟอร์มอัตรากำลังตามวันที่/ช่วงเวลา RN/PN/หัวหน้าเวรและทักษะ เป้าชั่วโมง/วันหยุด/โควตารายบุคคล และความต้องการเวร ตาม schema ที่ backend รองรับจริง
- [ ] เชื่อมการอ่านและจัดการประเภทเวรกับ service/repository เดิม ตรวจ router/OpenAPI และเติม endpoint ที่ขาดโดยไม่สร้างเส้นทางซ้ำ
- [ ] อ่านและบันทึก periods JSON จริง ตรวจช่วงเวลาถูกต้อง ชั่วโมงเวร และขอบเขตหน่วยงาน พร้อม optimistic concurrency สำหรับการแก้ไข
- [ ] แยกนโยบายร่างออกจากการยืนยันใช้งาน ไม่เปลี่ยนเป็น confirmed โดยไม่มีการตรวจข้อมูลครบ
- [ ] รีเซ็ตค่าในฟอร์มให้ตรง roster/หน่วยงาน/ฉบับที่เปิด ไม่ค้างค่าจาก useState ของบริบทก่อนหน้า
- [ ] แสดงผลกระทบของการเปลี่ยนตั้งค่าและทำให้ผล AUTO/summary ที่เก่ากว่าถูกระบุว่าล้าสมัย

เกณฑ์ผ่าน: ตั้งค่าหน่วยงานทดสอบผ่าน UI → โหลดใหม่ค่าตรงเดิม → readiness ใช้ค่าเดียวกัน; periods ไม่สูญหายหลังบันทึก/แก้ไข; viewer และการเข้าถึงข้ามหน่วยงานถูกบล็อก

### S13-04 — ความพร้อมและ workflow เชื่อมกันครบ (P1)

- [ ] เชื่อมหน้าเตรียมข้อมูลกับ readiness API จริง แทน Boolean ว่ามี roster/policy และให้เปิดฟอร์มแก้รายการที่ขาดได้
- [ ] แยกตำแหน่งหน้าที่กำลังดูออกจากสถานะ workflow จริง ไม่ทำให้การคลิกแท็บดูเหมือนตารางผ่านการอนุมัติแล้ว
- [ ] แสดงหลายปัญหาต่อเซลล์ โดย severity สูงสุดต้องไม่ถูก warning ทับ; ค้นหาได้ทั้งชื่อเจ้าหน้าที่ รหัสกฎ และวันที่
- [ ] คลิกปัญหาที่มีวันที่แล้วปิดแผงและโฟกัสช่อง/วันที่ได้; ปัญหาทั้งเดือนต้องมีรายละเอียดและทางแก้ ไม่เป็นปุ่มที่คลิกแล้วเงียบ
- [ ] แสดง validation report จากคำขอบันทึกที่ไม่ผ่าน ไม่แสดงเฉพาะ error กว้าง ๆ; ตรวจ flow ขอ override พร้อมเหตุผลหากอยู่ในสิทธิ์เดิม โดยห้ามเปิดใช้อัตโนมัติ
- [ ] ทดสอบ AUTO: ตรวจความพร้อม → สร้างข้อเสนอ → ตรวจผล → ใช้ผล; partial/infeasible/stale/simulation ต้องไม่ถูกใช้เป็นผลพร้อมประกาศ
- [ ] ตรวจส่งตรวจ/ส่งกลับพร้อมเหตุผล/อนุมัติ/ประกาศ/เปิดฉบับย้อนหลัง ให้ตรง status machine และสิทธิ์ API
- [ ] ป้องกัน response มาถึงสลับลำดับระหว่างเปลี่ยนหน่วยงาน เดือน ฉบับ หรือออกจากระบบ โดยยกเลิกหรือทิ้งผลที่ไม่ตรงบริบท

เกณฑ์ผ่าน: หัวหน้าหอผู้ป่วยทำ workflow ครบโดยไม่เรียก API เอง; viewer ดูได้แต่แก้ไม่ได้; ฉบับประกาศแก้ตรงไม่ได้; การเปลี่ยนบริบทไม่แสดงหรือบันทึกตารางผิดเดือน/ผิดหน่วยงาน

## 4. API / ข้อมูล / ความเข้ากันได้

- ใช้ API เดิมเป็นหลัก รวม assignments, summary, readiness และ solver; เปลี่ยน contract เฉพาะส่วนที่จำเป็น พร้อมแก้ docs/openapi.yaml และ contract tests
- shiftCode ว่างเป็นเซลล์ยังไม่จัดที่มี version ไม่ใช่ OFF/ลา; ตรวจทุก consumer เช่น validator, solver snapshot, summary, export, version diff และ audit ให้ตีความสอดคล้องกัน
- ตรวจว่า schema เดิมรองรับค่าว่างและ periods จริง หากจำเป็นต้อง migrate ให้เพิ่ม migration ใหม่ ห้ามแก้ประวัติ migration ที่ใช้แล้ว
- Endpoint เก่า POST /api/v1/schedules/generate ยังเป็น 501 ไม่ได้แปลว่า Solver ใหม่ไม่มี implementation; ตรวจผู้เรียกและระบุ deprecation ให้ชัดแทนการสร้าง solver ซ้ำ
- ระบบยืนยันตัวตนยังเป็น server-provisioned bearer credentials; SSO เป็นงานแยก ไม่ถือว่าเป็นเงื่อนไขปิด Sprint นี้
