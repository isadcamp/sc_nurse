# Sprint 12 — แก้ระบบให้ใช้งานได้จริงและปรับ UX/UI สำหรับหัวหน้าหอผู้ป่วย

สถานะ: วางแผนแล้ว ยังไม่เริ่มแก้โค้ดตามแผนนี้
วันที่: 2026-09-14
ที่มา: การตรวจโค้ดและหารือกับผู้ใช้ ต่อเนื่องจาก [Sprint 11](plan_s11.md)

## 1. เป้าหมายและขอบเขต

ให้หัวหน้าหอผู้ป่วยใช้งานได้ครบตั้งแต่เข้าสู่ระบบ เตรียมข้อมูล จัดเวร ตรวจและแก้ปัญหา ส่งตรวจ อนุมัติ จนประกาศและพิมพ์ตาราง โดยนำร่องหนึ่งหอผู้ป่วยหนึ่งเดือน

- ผู้ใช้ยืนยันว่าพบทั้งเปิดระบบไม่ได้และเปิดได้แต่ทำงานไม่ครบ
- คง Next.js, Go และ MySQL ต่อยอดโค้ดเดิม ไม่เขียนใหม่ทั้งระบบ
- แก้การทำงานและความถูกต้องก่อนปรับหน้าจอทั้งชุด
- ยังไม่เพิ่ม AI, SSO หรือหน้าพยาบาลสำหรับขอลา/แลกเวรในรอบนี้
- ใช้กฎเวรที่หน่วยงานยืนยัน ไม่สมมติอัตรากำลังหรือชั่วโมงพักขึ้นเอง

## 3. แผนดำเนินงานตามลำดับ

### ระยะ 1 — เปิดระบบและเชื่อมต่อให้ถูกต้อง

- [ ] ตรวจโปรเซสที่ใช้พอร์ต 8080 และกำหนด frontend/API ไม่ให้ชนบริการอื่น โดยไม่หยุดบริการที่ไม่เกี่ยวข้อง
- [ ] ตรวจ environment, API URL, CORS origin, MySQL และสถานะ migration แบบอ่านอย่างเดียวก่อน
- [ ] หากต้องเปลี่ยน schema ให้สำรองข้อมูลก่อน ใช้ migration ใหม่ ไม่แก้ migration ที่ใช้แล้ว
- [ ] เพิ่มหน้ากรอกรหัสเข้าใช้งานด้วย Bearer credentials เดิม ลบ token ตายตัวออกจาก frontend
- [ ] เรียก `/api/v1/auth/me` ตาม router จริงเพื่อนำตัวตน บทบาท และหน่วยงานมาแสดง; ตรวจเส้นทางก่อนเชื่อม UI
- [ ] เก็บ token ในหน่วยความจำของหน้า มีออกจากระบบและล้างข้อมูลเมื่อออกจากระบบ ไม่ใส่ token ใน log หรือ Git
- [ ] แสดงข้อความแยก API ติดต่อไม่ได้ รหัสไม่ถูกต้อง ไม่มีสิทธิ์ และไม่มีข้อมูล พร้อมลองใหม่
- [ ] ปรับ README และคู่มือให้เปิดบริการตามขั้นตอนได้จริง รวมค่าตัวอย่างที่ไม่มีความลับ

เกณฑ์ผ่าน: เปิดหน้าเว็บ ยืนยันตัวตน โหลดหน่วยงานและตารางจากฐานข้อมูลทดสอบได้ และเริ่มระบบใหม่ตามคู่มือได้สำเร็จ

### ระยะ 2 — แก้ความถูกต้องของงานจัดเวร

- [ ] ส่ง version และ reason สำหรับล็อก/ปลดล็อกตามสัญญา API
- [ ] ใช้ override เป็น false โดยปริยาย แสดงผลตรวจก่อนบันทึก; ให้เฉพาะผู้มีสิทธิ์เลือกยกเว้นพร้อมเหตุผลเองและบันทึก audit
- [ ] ใช้ validator กลางเดิมในการตรวจและบันทึก ไม่สร้างกฎซ้ำเฉพาะ frontend
- [ ] เมื่อเปลี่ยนเดือน/หน่วยงาน ล้างตารางเก่าและโหลดบริบทใหม่ ยกเลิกหรือเพิกเฉย response เก่า
- [ ] แสดงสถานะกำลังบันทึก/สำเร็จ/ล้มเหลว ป้องกันการแก้ไขซ้อนระหว่าง request ยังไม่จบ
- [ ] เมื่อ version ชนกัน แจ้งผู้ใช้และโหลดข้อมูลล่าสุด ไม่ retry เพื่อเขียนทับโดยเงียบ
- [ ] ตรวจสิทธิ์ head/viewer และขอบเขตหน่วยงานทุก endpoint ที่เกี่ยวข้อง ไม่พึ่งการซ่อนปุ่มอย่างเดียว
- [ ] ตรวจ transition ส่งตรวจ ส่งกลับ อนุมัติ ประกาศ และการสร้างฉบับแก้ไขหลังประกาศให้ตรง workflow เดิม

เกณฑ์ผ่าน: แก้เวร ล็อก ตรวจปัญหา และ workflow สำเร็จตามสิทธิ์และสถานะ โดยไม่มีการข้ามกฎโดยผู้ใช้ไม่ทราบ

### ระยะ 3 — ปรับ UX/UI ตามงานหัวหน้าหอผู้ป่วย

- [ ] เปิดระบบและเก็บภาพขั้นตอนจริง: เข้าสู่ระบบ เตรียมข้อมูล จัดเวร แก้ปัญหา ส่งตรวจ และประกาศ
- [ ] ใช้ภาพและปัญหาที่พบเลือกแบบหน้าจอปรับปรุงกับผู้ใช้ก่อนเปลี่ยน UI ทั้งชุด
- [ ] จัดเมนูเป็น ตารางเวร / ข้อมูลบุคลากร / วันลาและวันหยุด / กฎจัดเวร แยกงานตั้งค่าจากพื้นที่จัดเวร
- [ ] เพิ่มรายการตรวจความพร้อมจาก readiness backend พร้อมลิงก์แก้ข้อมูลที่ขาด
- [ ] ให้ตารางเป็นพื้นที่หลัก ตรึงชื่อและหัววันที่ แสดงหน่วยงาน/เดือน/ฉบับที่เปิดจริง และคำอธิบายรหัสเวร
- [ ] แสดงกำลังคนและปัญหาข้างตาราง กดไปเซลล์หรือวันที่ต้นเหตุได้ และแสดงหลายปัญหาต่อเซลล์ได้
- [ ] รองรับการเลือกและแก้เซลล์ด้วยคีย์บอร์ด มี focus ชัดเจน ไม่ใช้สีอย่างเดียวบอกปัญหา; modal มี label และจัดการ focus
- [ ] AUTO เป็นขั้นตอน ตรวจความพร้อม → สร้างข้อเสนอ → ตรวจผล → ใช้ผล ไม่บันทึกข้อเสนออัตโนมัติ
- [ ] ปุ่มส่งตรวจ/อนุมัติ/ประกาศแสดงตามสถานะและสิทธิ์ พร้อมผลตรวจและสถานะบันทึก
- [ ] ระบุฉบับประกาศในหน้าดูและเอกสารพิมพ์ให้ตรงกัน คง AI ไว้เป็นงานรอง

เกณฑ์ผ่าน: หัวหน้าหอผู้ป่วยทำงานหลักได้โดยไม่เรียก API เองหรือให้นักพัฒนาบอกปุ่มถัดไป และผ่านการตรวจหน้าจอจริงบนคอมพิวเตอร์ที่ใช้จัดเวร

### ระยะ 4 — ทดสอบครบวงจรและนำร่อง

- [ ] แก้ lint errors และตรวจ warnings ที่เหลือ พร้อม frontend build และ backend tests
- [ ] ปรับ E2E ให้ตรง UI โดยคงทดสอบการยืนยันตัวตน กฎเวร และการ override อย่างชัดเจน
- [ ] ทดสอบฐานข้อมูลแยกจากข้อมูลใช้งานจริง รวม migration และการเก็บข้อมูลหลัง restart
- [ ] ให้หัวหน้าหอผู้ป่วยยืนยันข้อมูลและกฎ แล้วทดลองหนึ่งเดือน ตรวจจำนวนคน เวร วันลา และเอกสารพิมพ์
- [ ] เตรียมสำรอง/กู้คืนและขั้นตอนกลับไปใช้รุ่นก่อน โดยไม่ลบตารางเวรหรือ audit เพื่อแก้ปัญหา
- [ ] ติดตามการเชื่อมต่อ บันทึกไม่สำเร็จ version conflict และ AUTO ล้มเหลว โดยไม่เก็บ token ใน log

เกณฑ์ผ่าน: จัดตารางจนประกาศและพิมพ์ได้ ข้อมูลคงอยู่หลัง restart ผู้ใช้ยอมรับผล และไม่มี P0/P1 ที่กระทบงานหลักค้างอยู่

## 4. API และกรณีทดสอบ

ใช้ API เดิมเป็นหลัก ตรวจ request/response กับ router และ OpenAPI ก่อนเชื่อมหน้าจอ ปรับเอกสารให้ตรงพฤติกรรมที่ยืนยัน ไม่สร้าง API จัดเวรใหม่ซ้ำของเดิม

- [ ] รหัสถูก/ผิด/ไม่ได้ส่ง, head/viewer และการเข้าถึงข้ามหน่วยงาน
- [ ] เดือน 28/29/30/31 วัน ข้อมูลว่าง เปลี่ยนบริบทระหว่างโหลด และ response มาถึงสลับลำดับ
- [ ] เวรทับลา พักไม่พอ คนไม่ครบ รอยต่อเดือน และ override พร้อม/ไม่มีเหตุผล
- [ ] ล็อก/ปลดล็อกพร้อม version, ข้อมูลชนกัน และเครือข่ายขาดระหว่างบันทึก
- [ ] AUTO ข้อมูลไม่พร้อม ยกเลิก timeout ผลไม่ครบ ผลล้าสมัย และการใช้ผล complete
- [ ] ส่งตรวจ ส่งกลับ อนุมัติ ประกาศ และการป้องกันแก้ฉบับประกาศโดยตรง
- [ ] คีย์บอร์ด focus modal การอ่านรหัสเวร และความตรงกันของข้อมูลหน้าจอกับเอกสารพิมพ์

## 5. ลำดับส่งมอบและเงื่อนไขปิด Sprint

ส่งมอบตามระยะ 1 → 2 → 3 → 4 โดยแต่ละระยะต้องผ่านเกณฑ์ก่อนขยายงาน พิจารณาเวลาและวันนำร่องหลังยืนยันสภาพบริการ ฐานข้อมูล และแบบหน้าจอแล้ว

Sprint นี้ถือว่าเสร็จเมื่อ workflow ของหัวหน้าหอผู้ป่วยทำงานครบกับฐานข้อมูลทดสอบ ผ่านการตรวจหน้าจอจริงและนำร่องที่ผู้ใช้ยอมรับ พร้อมคู่มือและผลทดสอบรอบล่าสุด ไม่ถือการสร้างเอกสารแผนนี้เป็นการแก้ระบบสำเร็จ
